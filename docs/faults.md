# 保护项注入测试（阶段 4.6 / Gate 4 的最后一关）

> 2026-11-20 ｜ 29 项全部通过 ｜ 原始数据 `out/fault_injection.json`
> 复跑：`bash run_fault_tests.sh`（约 100 s）

## 1. 这份测试要回答的问题

写保护代码最大的坑不是"没写"，而是"写了但从来没被触发过"。
`if 超时: raise` 这种代码在仿真里跑一万轮也不会执行一次，你无法确认它：

1. 判据对不对（阈值、单位、符号）；
2. 触发之后**到底有没有把指令发出去**——如果它在"已经决定要停"之后仍然发了一条，
   或者抛异常的位置在 `publisher.Write` 之后，那这条保护就是装饰品；
3. 会不会误杀正常工况（误报和漏报一样糟）。

所以每个保护项都需要一次**故意的、可复现的**注入：造出它该管的那种坏输入，
然后数"Write 被调了几次"。数量必须是 0。

## 2. 三层结构（越往后越接近真机）

| 层 | 跑在哪 | 覆盖什么 | 结果 |
|---|---|---|---|
| A 进程内 | 不起 DDS，`Runner` + 记录型 publisher | 所有 Guard 的判据与"这一拍不发指令" | 14/14 |
| A' 解码层 | 直接喂坏 LowState 报文 | 坏包不会污染状态缓存 | 5/5 |
| B 进程级 | 真 DDS：假机器人 + 真 `scan.py` + 总线旁观者 | 真程序在真总线上会停、停了就不再发 | 8/8 |
| C 仿真器对抗 | 真 MuJoCo 仿真器 | 仿真器本身不是来者不拒 | 2/2 |

B 层为什么必须有：A 层用的是 `Runner` + 假 publisher，只能证明"这个类被单测过了"。
B 层跑的是 `python3 r1d_scan/scan.py` 本尊，坏状态由 `r1d_scan/fake_robot.py` 注入，
另有第三个进程订阅 `rt/lowcmd` 数总线上的帧——**程序说自己停了**和**总线上真的没帧了**是两件事。

C 层为什么必须有：如果仿真器接受一切坏指令，那么"仿真闭环里指令拒绝数 0"就是一句废话。
C 层证明：坏 CRC / 模式不匹配 / NaN 的 LowCmd 会被仿真器拒掉，物理一步都不走（物理 0 步）。

### B 层：真 DDS 上"多久停下"

注入时刻与 `scan.py` 最后一条指令时刻都是 `CLOCK_MONOTONIC`，同一台机器上可直接相减。

| 注入 | 检测延迟 | 停止延迟 | 说明 |
|---|---|---|---|
| 故障字 | 6–8 ms | **2–7 ms** | 一条状态就判死 |
| 电机过热 | 6–8 ms | **3–6 ms** | 同上 |
| 模式变化 | 6–10 ms | **2–7 ms** | 同上 |
| 坏 CRC | ~203 ms | **198–201 ms** | 坏包被逐条丢弃 → 状态变陈旧 → 0.2 s 超时兜底 |
| tick 倒退 | ~201 ms | **198–201 ms** | 同上 |
| 报文 NaN | ~202 ms | **198–201 ms** | 同上 |
| 链路中断 | ~200 ms | **198–200 ms** | 同上 |

三种直接故障 3–7 ms 就停，说明"看到了坏状态 ⇒ 下一拍不发"是真的。
四种链路级故障统一停在 200 ms，正是 `state_timeout=0.20` 的设计值——不是巧合，是同一个闸门。

**200 ms 意味着什么**：扫描峰值 0.037 m/s × 0.2 s ≈ **7.4 mm** 的盲走距离。
相对 100 mm 的绝对定位预算、200 mm 的工作距，都是安全的。

**"停"的含义**：停止发送新指令，**不清零 KP/KD**。机器人继续执行最后一条指令
（保持姿态），这是 `TASKS.md` 安全红线的要求——清零等于让手臂自由落体。

## 4. 这次注入测试抓出来的两个真问题

1. **`mode_machine` 没有保护**。原来只查 `mode_pr`，机型/固件族标识变了照样发指令。
   已补（`Controller.expected_mode_machine`），并由第 4 条覆盖。
2. **假机器人把 dq 算错了**。最初 `dq = Δq / 0.002`，DDS 抖动把几条指令攒在一起送达时，
   0.002 s 的分母把速度放大到 3.3 rad/s，健康对照直接误触"预计力矩超预算"（关节 5，−9.2 N·m）。
   改成 `Δq / 真实耗时` 后才通过。
   顺带说明一个真机上的敏感性：小关节（腕部 effort=10 N·m）的力矩预算 9 N·m 里，
   `kd·q̇` 项在 dq 噪声下很容易吃掉一半。阶段 5 要盯 `dq` 的质量。

## 5. 已知限制（不要在真机上默认这些数字）

| 项 | 现状 | 真机要做什么 |
|---|---|---|
| 指令频率 | 实测 320–410 Hz（虚拟机 `time.sleep` 粒度 ~1.15 ms 所致；单拍计算量仅 ~0.7 ms：编码 274 µs + 发布 435 µs + 重力前馈 9 µs） | 原生 Linux 上复测，预期接近 500 Hz |
| 仿真器接收 | 发 320–400 Hz、仿真器实际发布 ~200–260 Hz（2 核虚拟机 + 软件渲染时的上限） | 真机由电机侧决定，不受此限 |
| 虚拟机负载 | 带窗口跑且机器被占用时，控制循环可能停顿 >70 ms 并触发保护——**保护在工作，不是 bug**；已去掉每帧多余的 `mj_forward`、视图刷新降到 20 Hz 减负 | 用专用控制机，不要在跑的时候开别的重任务 |
| 窗口退出 | MuJoCo 被动视图在解释器析构时偶发段错误（报告已落盘，无实际影响）；已在写盘后跳过析构退出 | 不涉及 |
| 力矩预算 | 用 URDF effort × 0.9 | 换成厂商连续力矩 + 实测温升 |
| 槽位 / KP / KD | `slot_source: provisional` | 阶段 5 只读核对后替换，再重跑一遍仿真回归 |
