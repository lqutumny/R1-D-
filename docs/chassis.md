# 底盘运动与升降柱（阶段 6）

> 2026-11-23 ｜ 状态：**仿真里都走通了**，真机未动
> 底盘有**两种**动作，别混：**平移**（`Move`，轮子）和**立柱伸缩**（`HeightAdjust`，升降柱）。
> 实际要做的是后者——探头高度靠立柱粗调。

## 1. 一句话

底盘和手臂走的是**两条互不相干的通道**：手臂是低层电机指令（`rt/lowcmd`），
底盘是 RPC 服务（`agv`）。所以"底盘先动起来"这件事不用碰已经跑通的扫描代码。

## 2. 接口事实（从 SDK 头文件确认，不是猜的）

来源：本机 `/usr/local/include/unitree/robot/g1/agv/g1_agv_api.hpp`、`g1_agv_client.hpp`，
以及 `example/g1/g1d/g1_agv_client_example.cpp`。

| 项 | 值 |
|---|---|
| 服务名 | `agv` |
| API 版本 | `1.0.0.1` |
| `Move`（1001） | 参数 JSON `{"vx","vy","vyaw"}`，单位 **m/s、m/s、rad/s** |
| `HeightAdjust`（1002） | 参数 JSON `{"data": vz}`，vz 是**归一化** [-1, 1]，× **76.5 mm/s** 才是立柱速度 |

两个坑：

1. **升降柱不是米制。** `HeightAdjust(0.5)` 是"半速上升"，不是 0.5 m/s；
   写成米制会以约 6.5 倍速冲出去。
2. **`Move` 是速度指令，不是位移。** 发一次就一直走，必须持续发或由固件超时停止。

## 3. 为什么底盘以前不建模

`models/r1_a7.urdf` 只有 pelvis + 腰 + 双臂 + 头（17 个 revolute，1 个 fixed），
**没有底盘、没有轮子**。而低层接管拿到的 `rt/lowcmd` 里也只有那 14 个臂部电机槽。
所以旧版 `build_scene.py` 直接把根 body 焊死在世界上——不是偷懒，是当时没有底盘这条通道。

## 4. 仿真里怎么做的（阶段 1：运动学底盘）

```bash
python3 tools/build_scene.py --mobile          # 生成 models/r1_a7_scene_mobile.xml
python3 r1d_scan/sim.py --network lo --mobile  # 终端 1：托管 agv 服务
python3 tools/chassis_demo.py --network lo \
    --plan forward:0.4,left:90,forward:0.4     # 终端 2：让底盘走
```

三处改动：

| 位置 | 改动 |
|---|---|
| `tools/build_scene.py --mobile` | 根 body 加 `freejoint`（nq 17→24），底盘板/立柱挂到 mount 上跟着走，另存 `r1_a7_scene_mobile.xml` + `simulation_mobile.json` |
| `r1d_scan/sim.py --mobile` | 托管 `agv` 服务（1001/1002）；每步把底盘速度写进自由关节，步进后把底座投影回水平 |
| `r1d_scan/chassis.py` | 客户端：限幅 + 看门狗 + `drive()`；仿真和真机同一份 |

### 运动学底盘 = 什么做了、什么没做

| 做了 | 没做 |
|---|---|
| 按 `(vx, vy, vyaw)` 准确平移/转向 | 轮地摩擦、打滑、轮径换算 |
| 底座姿态强制水平（俯仰/横滚=0） | 加减速时手臂的惯性耦合 |
| 手臂动力学在移动基座上照常积分 | 手臂反作用力推动底盘（每步速度被覆盖） |

**为什么先这样**：轮径、轮距、底盘质量都没实测，做成动力学底盘只是把一堆假设塞进物理引擎，
出错时也分不清是接口错了还是参数错了。阶段 2 再换（届时只需改 `sim.py`，`chassis.py` 不动）。

## 5. 安全设计

| 措施 | 位置 |
|---|---|
| 速度限幅（vx 0.20 / vy 0.10 / w 0.40） | `models/chassis.json` → `chassis.py` |
| 客户端看门狗：0.5 s 没再发就补零速 | `Chassis._watch` |
| 服务端兜底：0.5 s 没新指令就按零速算 | `sim.py` 的 `chassis_timeout` |
| 升降柱默认关闭，调用返回 `-9` 而不是"假装成功" | `models/chassis.json` 的 `height.enabled=false` |
| 零速探针：先确认服务存在再给速度 | `Chassis.probe()` |
| 每次 `drive()` 结束一定 `stop()`（`finally` 里） | `Chassis.drive` |

**服务缺失的实测特征**：在没有 `agv` 服务端的域上调用，返回码 **3102**、耗时约 1.9 s，
不抛异常。所以真机上"探针非 0"就是"这条通道不在"。

## 7. 上真机之前必须确认的四件事

1. **这台 R1-D 到底有没有 `agv` 服务**（零速探针，`Chassis.probe()`）。没有的话，底盘可能挂在
   `loco` 服务的 `SetVelocity(vx, vy, omega, duration)` 上——注意那是**带 duration 的速度**接口，
   语义和 `Move` 不同，需要另写一个约 20 行的后端（`chassis.py` 目前**只实现了 agv**，
   没有做假的后端抽象，等实测确认是哪条再说）。
2. **方向约定**：仿真里 +x 是正前方、+vyaw 是左转。真机必须先 0.05 m/s / 0.1 rad/s 各试一次，
   确认符号没反。
3. **低层接管和底盘服务能不能并存**：可能一进低层，固件就禁止底盘服务；也可能各管各的。
   这决定了以后"边走边扫"是可行还是必须"停-扫-走"。
4. **轮径/轮距/质量**：只影响阶段 2 的动力学底盘，现在不阻塞。

## 5.5 立柱伸缩（`HeightAdjust`）——实际要做的那个

```bash
# 生成伸缩场景（一次性）
python3 tools/build_scene.py --lift

# 终端 1：仿真器托管 agv 服务（--lift）
python3 r1d_scan/sim.py --network lo --domain 215 --lift

# 终端 2：升 10 cm、停 1 s、降 5 cm
python3 tools/lift_demo.py --network lo --domain 215 --plan up:0.10,wait:1,down:0.05
```

### 这条通道的三个数字

| 项 | 值 | 来源 |
|---|---|---|
| 服务 / API | `agv` / `1001 Move`、`1002 HeightAdjust` | SDK 头文件 |
| 立柱最高速度 | **76.5 mm/s** | 官方 `HeightAdjust` 注释 |
| 输入量 | **归一化 vz ∈ [-1, 1]**，×76.5 mm/s = 实际速度 | 同上；**不是米制** |
| 机械行程 | **10 – 90 cm**（离底盘板上表面，共 0.80 m） | **实测 2026-11-23，卷尺** |
| 可用行程 | **40 – 90 cm**（0.50 m） | 实测机械行程扣掉手臂磕碰段 |
| 为什么砍掉 0–40 cm | 立柱低于 40 cm 时**手臂会打到底盘** | 现场观察 |

### 为什么"位置"要自己算

真机 `HeightAdjust` 只吃速度、**不报位置**。所以：

- 走多少米 = 速度 × 时间，**开环**；
- `lift_demo.py --plan up:0.10` 会算好 2.6 s 再发（0.5 归一化 = 38.2 mm/s）；
- 到行程端头靠固件顶住（仿真里记 `column_limit_hits`，报告里能看到）。

### 没有位置反馈，怎么保证不撞手臂（关键）

这是立柱这条通道最危险的地方，和轮子不一样：轮子撞了顶多顶住，立柱往下走是**夹手臂**。

**问题**：`HeightAdjust` 只吃速度，读不到当前位置。开环积分会累积误差，而且**上电时不知道自己在哪**。
今天往上走 10 cm、明天往下走 20 cm，程序对"现在离底盘多高"一无所知。

**做法：用安全的那一端做基准——顶端，不是底端。**

| | 顶端（90 cm） | 底端（10 cm） |
|---|---|---|
| 上方空间 | 空的，顶到只是停住 | — |
| 手臂 | 不会碰到任何东西 | **会打到底盘** |
| 能不能当基准 | **能** | **不能** |

所以流程是：

1. 上电后**先慢速升到顶**（`--vz 0.2`，约 15 mm/s），到顶自然停住——这一刻的位置精确已知 = 90 cm。
2. 之后只做"从顶端往下 Δ"的动作，Δ 不超过 50 cm。
3. 每完成一段，若怀疑漂移，再回顶重新建立基准。

顶端归零还有个附带好处：它顺便验证了"上限方向"是对的——如果升的方向反了，你立刻就知道。

**仿真里为什么不用这套**：仿真能直接读关节位置（`HEIGHT` 那行），所以不需要归零。
但**真机必须按上面的流程走**，因为那才是真实的信息条件。

### 仿真里的立柱是运动学驱动（踩过的坑）

第一版我把速度写进滑动关节的 `qvel`，让 MuJoCo 自己积分。结果**速度凭空少了 26%**：
设 38.25 mm/s，实测只走 28.4 mm/s——因为重力在每个 1 ms 步里吃掉 `g·dt = 9.81 mm/s`，
停下时还会以约 1 cm/s 往下滑。真机立柱是螺杆传动、不会回落。

所以现在改成：**位置自己积分，每步把 qpos 写回去、速度清零**。速度由指令决定、与重力无关；
代价是"载重把立柱压回去"这类动力学没有建模（需要实测传动参数）。

### 场景结构（`--lift`）

```
world
├── floor / wall / light / cameras          静态
└── lift_base（固定）
    ├── base_plate                          底盘板（视觉，mass=0）
    ├── lift_sleeve                         外筒（视觉，mass=0）
    └── lift_column（滑动关节 lift_slide）
        ├── lift_mast                       内柱（mass=2，假设值）
        └── robot_mount                     上半身+手臂+探头
```

`nq` 17 → 18（多一个滑动自由度），总质量 17.56 → 19.56 kg（内柱那 2 kg 是假设）。

### 验证（`python3 tools/test_lift.py`，12/12 通过，18 s）

| 用例 | 结果 |
|---|---|
| 配置里已启用、行程区间合法 | 通过（range `[-0.15, 0.15]`，max_vz 0.5） |

| 未启用时返回 −9，不假装成功 | 通过 |
